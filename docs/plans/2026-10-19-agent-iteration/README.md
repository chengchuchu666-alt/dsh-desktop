# 后续迭代总计划与 Agent 执行入口

日期：2026-10-19。状态：**规划完成，实施任务尚未启动**。
调查基线：`26776d5`，分支 `codex/cc-connect-dsh-integration`。
本计划供后续执行会话使用；本轮交付是项目盘点、任务卡和交接协议。

## 1. 从哪里开始

1. 读[项目事实盘点](../2026-10-19-project-review.md)，理解目标、模块和已交付能力。
2. 读本页，了解优先级、依赖和执行边界。
3. 在[进度表](progress.md)选择一个可执行任务，再只读[任务卡](tasks.md)中对应章节。
4. 用[执行提示词](agent-prompt.md)启动后续 agent；一次只分配一个任务。

旧计划是设计和历史证据来源，不能直接把其中的 `todo` 当成最新待办。
正式需求与缺陷继续进入 GitHub Issues，规则见[Issue tracker](../../agents/issue-tracker.md)。
本计划的 IT 编号是任务分解编号；本轮没有创建、关闭或修改远端 issue。

## 2. 项目目标与产品边界

项目首先要让用户**下载安装后，稳定使用官方 Harness，出错后能自助恢复**。
官方 Agent、模型与工具逻辑继续由上游负责。壳负责交付运行时、桌面入口、进程管理、
更新、恢复、诊断，以及已经接入的飞书、LAN、垃圾桶和多版本运行环境。

当前范围以已接受的 [ADR 0030](../../decisions/0030-reliable-electron-shell-scope.zh.md)、
[0034](../../decisions/0034-multi-runtime-dashboard.zh.md)、
[0037](../../decisions/0037-feishu-application-manager.zh.md)、
[0038](../../decisions/0038-close-main-window-quits.zh.md) 的组合解释：

- 主界面仍是官方 WebUI；不重建聊天产品、Agent 工作台或模型平台。
- 官方多 Runtime / Environment MVP 已存在；后续先补可靠性，再补管理体验。
- 社区 Edition 目前是来源目录；安装 Adapter、自动升级和 OS 沙箱尚未交付。
- 社区插件由用户手动安装；数据隔离不等于恶意代码隔离。
- 主窗口关闭走应用退出流程；旧计划中的“关闭到托盘”不再作为实现要求。
- 签名、公证、远程控制、社区二进制执行等继续按专项决策处理。

## 4. 按结果推进，避免同时展开三条路线

### 第一阶段：可信基线与文档收口

任务：IT-00～IT-03、IT-16～IT-18。IT-16 是只读工作树盘点；IT-17/18 先复核 E2E 判定与进程归属契约。

交付：执行时的版本/资源/远端状态一致；locale 失败有可复核解释或修复；当前状态文档
与代码一致；旧计划对照表明确哪些已完成、哪些待设计、哪些仅历史参考。
文档任务可在 locale 诊断期间独立推进，但代码收口必须处理基线失败。
E2E wrapper 的摘要判定和全局进程名清理是静态风险，尚未动态复现；受控复核期间
不直接在共享开发机运行旧 wrapper。新行为进入候选交付前，先保证门禁不会误判或影响别的任务。

### 第二阶段：已有多版本功能可靠性

任务：IT-04～IT-07、IT-19/20；IT-08 是可并行的 Windows 证据任务。

交付：Runtime 异常退出和数据保留有测试；同环境生命周期竞争有明确契约；设置页状态
与主进程一致、错误可重试。保留已有 MVP，不接入社区应用安装器，不重构整个设置面板。
目录来源与隔离语义明确，诊断能区分 bundled 与 selected kernel，减少版本判断错误。

这组任务会改善用户已能操作的功能；不以新增设置项数量评价进展。

### 第三阶段：数据与任务保护

任务：IT-09～IT-13。兼容调查、任务状态调查可以并行，实施必须经过对应设计审查。

交付：精确版本的数据兼容证据、所有内核回退入口的保护规范、可信任务状态和退出/更新
授权规范。旧 A02～A06 提供研究起点；本计划没有把这些高风险项直接标成可交给弱模型实现。

在新 ADR 和分解卡通过前，现有退出/自动更新行为保持现状，也不能先把新能力写进官网。

### 第四阶段：持续维护与候选交付

任务：IT-14、IT-15；IT-21 是版本查询有界失败的小改进。
IT-14/15 是每轮维护与收口模板，不代表现在创建定时任务或启动发版。

交付：新反馈被复现、重复项和已修复项有证据；本轮候选通过必要门禁后形成可审查的交付包。
正式发布由获得发布授权的执行会话调用[发布技能](../../../.agents/skills/release-dsh-desktop/SKILL.md)。

后续产品候选按 ADR 0034 的 P1 顺序考虑：版本目录、安装进度/失败重试、环境重命名和日志入口。
每次只选一个用户路径，先补明确任务卡再实现。取消/断点续传、社区 Adapter、快照恢复、L4 沙箱
均不能混入第一批可靠性小任务。

依赖和准入以[进度表](progress.md)为准。跨分支、跨 Worktree 的成果必须对照提交和实际代码，
不能因为存在同名文件或远端 PR 就算已合入当前分支。

低性能 agent 一次一项，默认最多 3 个产品/测试文件；证据和 progress 另计。
超过两次同因失败仍无新证据、需要改更多模块或出现未定产品选择时，记录阻塞和最小建议，
交给审查者细分。不能通过跳过测试、放宽校验、加通用重试来达成“绿灯”。

## 6. 持续迭代规则

每一轮执行以下闭环，保存到本轮 evidence，而不是默认新增遥测：

1. **收集**：只读核对用户反馈、open issue/PR、失败 CI、上游版本公告；记录时间和 SHA。
2. **筛选**：数据丢失/启动阻断优先，其次可复现缺陷、已有功能可靠性，再考虑新功能。
   没有复现证据的投诉先做诊断卡；已发布修复先核实用户版本。
3. **定界**：写出触发条件、前后行为、允许文件、非目标、测试和停止条件；至少一个明确用户收益。
4. **执行**：独立小改动，按仓库指令实现与验证；新设计留给审查者，弱模型执行已经定界的卡。
5. **复核**：检查产品范围、数据归属、IPC 来源、并发、退出清理和文档事实；只检查本任务相关部分。
6. **交接**：记录实际命令/退出码/未覆盖场景。合并、推送、issue 回复和发布分别服从执行会话授权。

每轮最多一个功能主题加必要维护。P0 故障可以打断功能主题；没有必要改动时允许仅更新诊断
与证据，不为了“自我进化”制造功能、版本号或扩大产品范围。

衡量结果用四项：同类问题是否复发、用户路径是否通过、回归是否有意义、交接是否可复现。
下载量/Star 仅作为采样指标；不据此推导活跃用户，也不继续扩大刚完成的官网改版。
